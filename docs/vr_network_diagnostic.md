# VR两分钟独立网络诊断

用途：查清手柄持续发送时，为什么FluxVLA偶尔几百毫秒拿不到新位姿。程序强制只接VR，保留当前头显面板和A键菜单；不连接机械臂、相机、夹爪，不创建训练数据，不改遥操作参数。

## 运行

先退出原来的VR程序，避免8442/8443端口被占用。进入FluxVLA环境：

```bash
cd /home/robot/VLA/FluxVLA
conda activate fluxvla
python scripts/diagnose_vr_network.py --vr-ip 192.168.110.211
```

这里填写的是**头显IP**，不是Thor或机器人IP。本次头显是192.168.110.211，换网络或重新分配地址后应填写实际地址。

1. 用头显打开程序最后打印的“头显打开”网址，刷新网页并进入VR。程序按到头显的实际路由选择网卡和访问地址，避免把VPN虚拟地址当作VR网址。
2. 两个手柄追踪正常后自动开始120秒计时。正常移动、按侧键和操作A菜单即可；这些按键不会驱动机器人或夹爪。头显沿用只读按键检查面板，终端每15秒显示剩余时间。
3. 两分钟到时自动停止抓包、保存报告和释放端口。Ctrl+C可提前结束并保留证据，报告会标记未完成正常时长。

等待进入VR的时间另计，默认最多90秒；刚开程序没有戴头显，不会消耗正式测试时间。两分钟没有复现也会如实报告，不代表以后绝不发生。

工具已在本机安装。另一台机器首次使用需要：

```bash
sudo apt-get install tcpdump tshark
```

程序本身不需要sudo运行。抓包子进程使用`sudo -n`；如果提示权限不足，先单独执行`sudo -v`，再运行原命令。仅抓指定头显IP和VR WebSocket端口，保留160字节包头快照；不用解密手柄数据，也不捕获机器人控制端口。默认端口沿用配置，通常8442。

## 看结果

程序结束打印报告位置。每轮放在独立目录：

```text
work_dirs/a10/vr/network_checks/<本次时间目录>/
  report.md       中文结论，优先看这个
  report.json     每次异常的归因和证据
  summary.json    原有延迟指标＋接收事件循环心跳延迟
  events.jsonl    发包/收包/首次读取/心跳/队列长度逐条记录
  network.pcap    原始网络抓包
  network.tsv     tshark解析后的包头时序
  tcpdump.log     抓包是否成功、有没有丢记录
```

心跳每50毫秒在**接收WebSocket的同一个事件循环**运行。它不是另一个独立线程的“我还活着”，能反映实际接收循环的调度停顿。原有发包、收包、控制循环首次读取指标继续复用。

| 报告提示 | 含义 |
|---|---|
| 浏览器停止发位姿 | 发包间隔本身超过250ms，结合VR失焦/追踪状态检查 |
| 停顿在Thor抓包入口之前 | 心跳正常，这段时间未观察到相应TCP连接的有效载荷进入Thor；继续查发送侧和链路 |
| 发现TCP交付异常线索 | 有重传、乱序、缺段或零窗口标志，不能直接等同Wi-Fi丢包 |
| 接收事件循环延迟 | 对应连接的数据持续到达，但接收循环心跳明显推迟 |
| 数据已到Thor，检查TCP/TLS/WebSocket交付 | 心跳正常且有入站数据，继续检查传输重组、TLS或消息组帧 |
| 证据不完整／暂不能归因 | 抓包/诊断丢记录、IP不匹配、心跳缺失或两类异常同时出现，不强行下结论 |

只比较同一连接、同一次停顿。250ms是异常筛选门槛，不是测出来的固定网络延迟；不将不同设备的绝对时钟相减。Thor抓包入口也不是Wi-Fi空口，无法单凭本报告认定具体射频干扰。

测试时长可选`--duration 120`，等待时长可选`--wait-timeout 90`。默认即可，不用在原来的长采集命令上追加这些参数。本机合成验收位于network_checks/selftest下，明确标记synthetic，不是实际头显或Wi-Fi稳定性证明。
