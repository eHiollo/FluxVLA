# 双臂 VR 数据采集：手柄、头显与终端

2026-11-12，分支 `kaanh_lerobot_recording`：默认使用原 LeRobot 工具链的 **LeRobotDataset**，采集阶段顺序也对齐原 `lerobot_record.record()`。夹爪故障保留VR和录制界面，不自动清报警。已完成离线验证，真机录制仍需操作者验收。第8节起保留历史记录，与当前默认不一致时以第2、3、6、14节为准。

## 1. 先确认右手 A 键（不接机器人）

在 `/home/robot/VLA/FluxVLA` 的 fluxvla 环境运行：

```bash
python scripts/teleoperate.py \
  --config configs/a10/a10_dual_arm_vr_teleop.py \
  --record-config configs/a10/a10_dual_arm_record.py \
  --check-record-buttons
```

打开终端显示的VR网址。程序只连接VR，不连接机械臂、夹爪、相机，不创建数据集。首次先松开右手功能键并把左摇杆回中：

1. 右手实体 A 键按下时，新版头显应立即展开左摇杆方向菜单，终端右手按钮应显示 `a: True`；按摇杆本身不应激活菜单。
2. 按住 A，左摇杆先回中，再依次向右/左/下/上拨动，检查 `BUTTON EVENT: right/left/down/up`，每次回中才能触发下一次。
3. 斜拨不触发；保持方向不重复触发；松开 A 后左摇杆回中。
4. Ctrl+C退出。若实体键不对应，请提供终端的 `pressed` 索引和 `mapping`，不要直接拿未确认按键上实机。

本次修正了旧网页将 buttons[3] 当成 A 的问题：在 `xr-standard` 中3是摇杆按压，2是触摸板。A/B默认采用后续4/5位置，仍需现场确认设备对应；非 `xr-standard` 不猜测其含义。参考 [WebXR Gamepads映射规范](https://www.w3.org/TR/webxr-gamepads-module-1/#xr-standard-gamepad-mapping)。按键通过配置 `capture.buttons.modifier_button` 选择 `a`/`b`/`thumbstick`，推荐右手A。修改网页后需要重新加载页面才能使用新代码。

## 2. 启动双臂实时采集

下面的命令启用真实遥操作能力；由现场操作者执行。机械臂须已正常连接并使能，三路相机和两个夹爪须已确认身份。程序不会自动使能，也不会启动后自动复位或录制。

```bash
python scripts/teleoperate.py \
  --config configs/a10/a10_dual_arm_vr_teleop.py \
  --record-config configs/a10/a10_dual_arm_record.py \
  --cfg-options \
    teleop.record_controller=False \
    teleop.vr_only=False \
    teleop.observe_only=False \
    teleop.operator.allow_motion=True \
    teleop.zx_grippers.enabled=True
```

这使用双臂配置当前默认运动参数；如需原来CLI中验证过的速度参数，可继续加在 `--cfg-options` 后面。本轮没有替换你的CLI或改变运动速度默认值。

- 任务文字默认 `Pick up the water bottle`，输出目录默认 `datasets/a10_dual_lerobot_record`。不要覆盖成旧 `datasets/a10_dual_record`，两个写入后端不混写。
- 首次目录必须为空。再次向同一数据集录制，在上述命令最后添加：

```bash
  --record-options record.resume=True
```

- 另开任务/数据集可添加（续行时注意上一行末尾的反斜杠）：

```bash
  --record-options \
    record.root=datasets/bottle_dual_01 \
    'capture.task=Pick up the water bottle'
```

- 意外退出留下未保存集时，先检查文件，再显式添加 `record.resume=True record.recover=True`，归档该集的图像和诊断后开始新集，不自动发布半集。原生保存阶段中断时保留现场、拒绝自动修复；改用新目录继续采集，原目录另行检查。
- `--preview` 检查配置，不连接设备或写数据。`--observe`、标定和数据录制互斥；`--record-controller` 可以额外记录控制器诊断，但不是训练数据。
- 相机路径发生变化时先单独运行 `python scripts/a10_devices.py --update`。启动时复用设备匹配工具核对序列号、彩色接口及稳定路径，不自动改配置。运行中掉线不重新绑定另一台设备。

## 3. 手柄操作

不按功能键时：左右摇杆X仍控制对应夹爪，侧键/扳机沿用现有运动方式。

| 按住右手A，再拨左摇杆 | 行为 |
|---|---|
| 右 | 准备阶段开始录制；录制中结束采样并进入整理场景；整理好后再向右，保存并自动录下一集 |
| 左 | 标记本集重录、进入整理场景；整理好后向右，废弃旧缓冲并自动重录同一集 |
| 下 | 停止录制；保存有效当前集后退出。已标记重录的集不发布；故障/空集保留待检查 |
| 上 | 请求双臂复位；两手释放、回中后再次向上确认 `m_init`；复位期间不采样，保留已有缓冲 |

进入模式后左摇杆先回中；退出模式后也要回中才恢复左夹爪输入。模式内只屏蔽左夹爪的新开合输入，右夹爪仍走正常输入；不要将它视为夹爪急停。方向需越过0.7阈值，另一轴须在回中区内；斜向忽略。

沿用旧流程：**准备 → 录制 → 整理场景（RESET）/准备重录（RERECORD）→ 保存/清空 → 自动下一集/重录本集**。RESET文字表示整理场景阶段，不代表自动执行机械臂回零；只有明确的UP复位操作才调用m_init。录制中第一次向右不再立刻保存，第二次向右表示场景已整理好，提交保存后自动开始下一集。

保存/废弃是数据操作，不是机械臂停止命令。复位期间不录机械臂返回初始位置的动作。复位成功后无需额外松开A再进入菜单：保持A、摇杆回中、向右即可；待机复位后开始第1集，有缓冲时先保存/重录再自动下一集。

二次确认默认8秒过期。不同操作、断流或检测到输入序号重启会取消待确认；断流恢复后需松开功能键并回中，不重放旧命令。数据异常只能丢弃或退出检查，不能强行发布为正常样本。

## 4. 复位与取消

两手侧键及前扳机均释放且输入新鲜时才接受复位确认。录制中请求复位先停采样、保留当前缓冲进入整理阶段。后台先停止笛卡尔跟随并确认 `inactive + Stopped`，再调用现有 `move_to_init`，使用机器人配置中的初始关节角，不重新定义初始位置。复位成功返回原准备/整理阶段，不丢失当前集。

复位期间暂停VR机器人目标发送和采集，夹爪收到零摇杆输入，不自动张开或掉使能。复位完成后再次确认停止，清空锚点，要求释放接管键后才能重新接管。

- 复位中“右A＋左摇杆下”或终端 `stop` 请求取消；输入断流也取消。
- Ctrl+C/退出会设置取消信号，必要时打断控制请求，先清理机器人再等待数据保存。
- 取消/复位失败后锁住本会话的运动接管，头显显示错误；核对控制器后退出并重新启动，不自动重试复位。
- 本程序的取消需要通讯和控制器响应，不等于硬件急停。

## 5. 头显状态与备用终端

头显沿用原工具链的简短英文状态（现有字体），保留集号、任务、时长和操作提示。状态标题单独着色：待机白色、录制绿色、保存/确认黄色、故障红色；正文为白色，底板加深。帧数、详细设备健康、按钮原始索引保留在终端 `status` 和日志中，异常信息在头显突出显示：

| 显示 | 含义 |
|---|---|
| RESET / RERECORD | 整理场景，准备开始/重录；不是自动回零 |
| STARTING / RECORDING | 正在开始 / 正在录制 |
| SAVING DATA / SAVE COMPLETE | 后台保存中 / 文件已提交成功 |
| RESET（结束一集之后） | 本集缓冲保留，场景整理好后向右保存并自动下一集 |
| INVALID EPISODE | 本集失效，不能正常保存 |
| RESETTING / RESET FAILED | 复位中 / 复位失败或取消 |
| BUTTON CHECK / NO MOTION | 仅检查VR按钮，无设备运动 |

按住右手A后，头显按上下左右位置显示左摇杆菜单，松开A收起；不可用项置灰。提示随当前阶段变化：

| 阶段 | 上 UP | 下 DOWN | 左 LEFT | 右 RIGHT |
|---|---|---|---|---|
| 准备 | RESET 请求复位（须释放两手接管键） | 停止录制入口 | 不可用 | START 开始（设备就绪后） |
| 录制中 | 暂停采样后请求RESET | STOP RECORDING 保存有效集并退出 | REDO / RESET SCENE 标记重录 | FINISH EP / RESET SCENE 结束本集采样 |
| 整理场景 | RESET | STOP RECORDING | REDO THIS EP | SAVE + NEXT 保存并自动下一集 |
| 准备重录/本集失效 | 故障需先处理 | 停止录制入口 | REDO THIS EP | 标记重录后DISCARD + START AGAIN；故障未解决不自动录 |
| 复位中 | 不可用 | CANCEL RESET 取消复位 | 不可用 | 不可用 |
| 保存/开始/丢弃处理中 | 不可用 | 排队停止，磁盘操作完成后退出 | 不可用 | 不可用 |

- `CENTER LEFT STICK`：左摇杆回中后才能接受下一次方向输入。
- 摇杆可以逐渐推动：离开回中区后，达到0.7方向阈值才触发一次。允许主方向明显占优的小幅斜拨（主轴至少为另一轴的1.25倍）；接近45度的模糊斜拨不触发，须回中重拨。
- `CONFIRM RESET`：回中后再次向上确认；复位依旧要求两手侧键/扳机释放。重录沿用旧LEFT标记、RIGHT提交的阶段操作。
- 只读按钮检查也显示方向菜单，但不会执行任何设备操作；头显只保留最近一次 `BUTTON EVENT`，完整按钮值在终端。
- A键、回中门槛、确认和状态变化在下一次控制循环立即推送；时长等常规信息仍默认2Hz刷新。VR断线后收起菜单并显示断线提示。
- 保存完成后显示约1.5秒 `SAVE COMPLETE`，再自动录下一集；提示不阻塞控制循环。设备/VR未就绪会等待，不带着故障自动开始。
- 保存成功只在文件提交完成后显示。停止采样仍不是停止机械臂。

**更新后需重启遥操作程序，并在头显浏览器刷新页面**，沿用原启动命令。可先使用上面的 `--check-record-buttons` 检查字号、颜色和四方向菜单，不连接设备。

终端备用命令：`start`、`save`、`discard`、`reset`、`stop`、`status`、`help`、`quit`。discard/reset也要重复确认。手柄和终端用同一状态机。终端EOF等同quit；无人值守启动时可设 `--record-options capture.terminal=False`，但本阶段建议现场监护。

## 6. 采样与错误处理

当前默认与旧 LeRobot 采集循环对齐：**执行本轮遥操作 → 获取实际机器人/夹爪反馈及后台相机图像 → `add_frame()` → 下一轮**。`save_episode()` 完成原生统计、视频和元数据保存；`clear_episode_buffer()` 废弃本集。复用已安装的库，不从旁边的lerobot仓库导入代码。

按物理左ID1、右ID0打包14维数据，三路相机字段不变。`action`继续使用本帧实测关节和夹爪状态的副本，保持已定的双臂训练约定，不能换成UDP末端控制包。数据格式见[双臂数据交接说明](a10_dual_dataset_handoff.md)。机器人和夹爪仍独占设备；录制仅读取真实缓存，不新增控制器WebSocket或串口连接。

默认配置集中在 `capture`：

- 相机/机器人接收年龄不超过0.15秒，夹爪不超过0.20秒。
- 各设备接收时间差不超过0.15秒。
- 原生模式下150ms采样间隔、名义30Hz累计漂移只记录，不因一次慢循环废弃整集。短暂设备反馈过期跳过该次采样，持续超过 `capture.max_missing_feedback_s=1.0` 秒仍失效。畸形数据、真实报警、相机异常和磁盘错误仍失效。
- 上述为初始阈值，**未做现场时间分布验收**。不要为了消除错误盲目放宽；先查看具体数据。

每台相机有独立帧编号和短缓存；允许在有效期内复用最近画面/反馈，并记录重复画面次数及原始接收时间。主机接收时刻不是相机曝光时间，不宣称硬同步。正常停止等待期间不添加帧，确认结束后从最新真实缓存继续采样；不将停止前的旧反馈冒充最新值。

每个真实采样只添加一次，不补帧、不补零、不刷新旧反馈时间戳。与原工具链一样，Parquet/视频时间轴为 `frame_index/30`；实际采样耗时、跳过次数、采样空窗保留在 `meta/xlevr_diagnostics/episode_*.jsonl`。**名义30Hz不代表严格实时采样**，训练前应检查空窗和实际帧率；不能把这次调整称为解决了底层延迟。

机器人故障仍执行原运动保护流程；单独的相机、编码或磁盘错误只使录制失效，不主动发新的运动指令。夹爪硬件报警/线程故障锁定目标并确认机械臂停止，保留VR界面；本集标记中断。LEFT标记重录，再RIGHT废弃缓冲；故障未解决和VR未重新接管前不自动开始新集。后台保存期间不接受新一集，DOWN停止请求可排到保存完成后退出。正常保存后按旧工具链自动进入下一集。

日志位置：现有 `work_dirs/a10/vr/dual_teleop_diagnostics.jsonl` 增加 `dataset_recording`，含阶段、帧数、实际采样频率、异常、确认状态。每集 `meta/xlevr_diagnostics/` 保存机器人/夹爪/相机接收时间、相机帧号、VR输入及下发目标等关联信息。原图像不会塞进JSONL。

## 8. VR 网络延迟诊断（2026-11-09）

在原启动命令中增加 **`--measure-vr-latency`** 即可；现有运动参数、头显录制菜单和数据格式保持不变。需要刷新头显网页，才能加载本次新增的计时代码。这里测的是**应用层往返耗时**，包含浏览器/电脑调度和网络传输，不等于纯网络延迟，也不是手动机械臂到达目标的总延迟。

建议做两组各约2分钟的对照，使用同一头显、网络和位置：

**第一组：只有VR和录制状态头显，不接设备。**

```bash
python scripts/teleoperate.py \
  --config configs/a10/a10_dual_arm_vr_teleop.py \
  --record-config configs/a10/a10_dual_arm_record.py \
  --check-record-buttons \
  --measure-vr-latency
```

进入VR后移动手柄，并按右A查看方向菜单。这是按钮检查，不会连接机械臂、夹爪、相机，也不创建数据集。

**第二组：当前真实采集负载。** 在你原来的完整采集命令中，仅增加一行：

```bash
  --measure-vr-latency \
```

放在 `--cfg-options` 前面最容易辨认，原有 `--record-controller`、`--record-options` 和速度参数全部保留。此模式仍具备真实控制能力；只想测网络时保持两手侧键及前扳机释放、摇杆回中，不触发复位。先待机约1分钟，再用右A+左摇杆右录一小段静止数据，保存后退出。**只启动录制入口还没有开始录制，不能代表写盘时的负载。** 可给本次测试单独指定 `record.root=datasets/vr_latency_test_01`；新目录不需要续录，已有目录需要 `record.resume=True`。

每组用Ctrl+C正常退出以生成汇总。头显增加一行：

- `WS RTT`：最近一次应用层往返耗时，每秒探测一次；长时间无回包显示等待，不沿用旧低延迟数值。
- `RX pose age`：服务器回包时，距最近一包带诊断标记的VR数据已经过去多久，不是单程网络延迟。
- `queue ... B`：浏览器发送队列积压的字节数。

终端会打印每次运行的独立目录：`work_dirs/a10/vr/latency/<时间_标识>/`。

| 文件/指标 | 用途 |
|---|---|
| `events.jsonl` | 发包序号、浏览器发送时刻、服务器接收时刻、左右手读取、探测、连接/断开；包含页面可见性、XR状态、手柄跟踪有效性和发送队列 |
| `summary.json` | 本次模式、样本数、中位数、P95、P99、最大值，间隔/耗时超过100ms、250ms的次数及日志丢记录情况 |
| `send_interval_ms` | 头显连续两包之间的间隔；大间隔说明发包本身暂停，不能直接归因于网络 |
| `receive_interval_ms` | 电脑连续收到两包的间隔；和发包间隔对照看是否存在传输/接收调度拥堵 |
| `application_rtt_ms` | 头显发探测到收到回包的耗时，只用头显自身的单调时钟计算 |
| `first_consume_delay_ms` | 一包数据到达WebSocket接收回调后，第一次被控制循环读取的耗时；包含解析、队列、映射及等待下一轮循环 |
| `consumed_age_ms` | 每次控制循环读取时的数据年龄；重复读取旧帧也记录，用于分析断流 |

P95表示95%的样本不超过该值。每项最多保留最近100000个样本计算分位数，累计次数/最大值覆盖整次运行；左右手读取按手分别计数。控制循环使用“最新快照”，未被读取的中间帧不计入读取延迟；这不代表网络丢包。不同连接的序号和间隔独立计算，重连不会制造一个假的超长发包间隔。

两个设备的时钟没有同步，**不直接用服务器时间减头显时间计算单程延迟**。本版不输出单程估算，避免给出虚假的精度。RTT每秒一次可能漏掉很短的尖峰，要结合逐包间隔、读取年龄和既有`teleop_diagnostics.jsonl`的同一墙钟时间一起判断。持续断流但未恢复时不会产生下一包间隔，可从探测记录的`pose_age_ms`、`browser_status.send_idle_ms`以及断线事件查看。序号缺口也不能等同于UDP丢包，本链路是WebSocket。

日志复用后台写入器，队列满只记录丢诊断计数。探测消息不会进入手柄输入队列，不刷新手柄的新鲜度或影响断流保护；诊断默认关闭。直接结束进程或断电可能没有汇总，已刷盘的JSONL仍可分析。若没有任何RTT/发包样本，先确认头显连接并刷新了新网页，不要把“没有样本”当成零延迟。

## 9. 双臂输入异常暂停与重新接管（2026-11-09）

实机双臂遥操作遇到手柄位置突跳、输入过期、明确的追踪丢失等已识别输入异常时，会丢弃异常目标、停止整组跟随，并确认`inactive + Stopped`，然后保留VR连接和录制操作入口。终端会显示“VR输入异常已暂停”，无需因这类输入异常重新启动整条命令。

按头显提示操作：

1. 红色`INPUT PAUSED / MOTION STOPPED`：松开**两手侧键和前扳机**，两个摇杆都回中。异常原因提示标的是实际LEFT/RIGHT手柄，日志同时保留内部机械臂名称，避免混淆。
2. 保持追踪有效、数据持续更新且没有位置突跳至少**0.5秒**。不要求手完全不动。输入再次跳变、过期、丢失追踪，或重新按住接管键/拨摇杆，都会重新等待稳定；重复读取同一帧不能完成恢复检查。
3. 黄色`INPUT STABLE / PRESS GRIP`：重新按下任一侧键才解除锁定。一直按着、只移动手柄、只按前扳机，都不会自动恢复。重新接管时先用当前手柄位置和机器人实际反馈建立新锚点，再开始跟随，不重发异常前的累计目标。之后左右手恢复独立接管。

夹爪在暂停期间不接收新的开合目标，USB工作线程仍读取状态；发送前尚未执行的旧请求会被取消。恢复时需要摇杆回中，再重新拨动才响应。不自动张开或掉使能，夹爪先前已经下发的有限目标不等同于被物理急停。

若正在录制，本集会停止采样并标记为`failed`，不能保存为正常训练样本；后台尚在开始录制时发生异常也会保留该失效标记。可用右A+左摇杆左、回中后再次向左确认丢弃。重新接管且处理完异常集后，再向右开始新集，避免把暂停前后拼成连续数据。暂停期间不能开始新集或执行`m_init`；已保存的集保留。

默认稳定时长写在`configs/a10/a10_dual_arm_vr_teleop.py`的`input_recovery_stable_s=.5`，也可在原命令的`--cfg-options`后设置`teleop.input_recovery_stable_s=1.0`，支持0.5～5秒。现有启动命令可以继续使用；更新后需**刷新头显网页**加载红/黄状态标题。较旧网页没有有效追踪字段时无法通过恢复门槛。

控制器故障、机器人反馈/通信异常、夹爪故障、停止未确认、未知映射故障或参考轨迹保护仍按原故障流程退出，不进入这种恢复流程。`--observe`只读模式也不声称已经停止实机。这次改动保留原2m/s手柄位置速度保护和原运动参数。

主诊断文件`work_dirs/a10/vr/dual_teleop_diagnostics.jsonl`新增`input_pause`：包含异常手柄/机械臂、原因、停止确认、稳定时长及突跳速度；`reference_control.state`暂停时为`input_paused`，解除锁定的当轮为`input_resumed`。控制器`stop_status`继续保留；暂停阶段不下发UDP目标。上述行为已通过离线测试，实机停止手感和头显可读性仍需现场确认。

## 10. 控制周期超时后的恢复（2026-11-12）
